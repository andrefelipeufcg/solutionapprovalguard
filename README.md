# Solution Approval Guard (GLPI 10+ Plugin)

[![GLPI 10.0+](https://img.shields.io/badge/GLPI-10.0%2B-blue.svg)](https://glpi-project.org/)
[![License: GPL v3+](https://img.shields.io/badge/License-GPL%20v3%2B-green.svg)](https://www.gnu.org/licenses/gpl-3.0.html)

**Solution Approval Guard** is a usability and process integrity plugin developed specifically for **GLPI 10+**. It allows administrators to control whether end users can enter text comments when they decide to **approve** a ticket solution.

## 🔍 The Problem (Motivation)

In standard GLPI behavior, when a technician proposes a solution to a ticket, the requester has two possible actions: **Approve** or **Refuse**.

However, there is a common usability deviation in production environments: some users write feedback indicating pending issues but mistakenly click the **Approve Solution** button.

**Real example:**
> *"The problem was partially solved, but I still don't have access to one of the secondary systems."* > *(The user writes this and clicks **Approve** instead of Refuse).*

### Consequences:
1. The ticket is closed and archived normally by the system.
2. The support team assumes the incident was 100% mitigated (since the status changed to Closed).
3. The user's feedback is forgotten in the ticket history, generating future rework and negatively impacting SLA indicators and actual customer satisfaction.

**Solution Approval Guard** solves this contradiction by forcing the user to make a linear decision: if there is something to comment/complain about, the solution must be refused; if the solution solved the problem, it must be approved with a clean text box.

---

## ✨ Features

- **Smart Rich Text Sanitization:** The plugin automatically cleans empty HTML tags (`<p></p>`, `<br>`) and space entities (`&nbsp;`) natively generated by GLPI's visual editor (TinyMCE), ensuring the block only occurs if the user actually typed real text.
- **Agnostic Request Interception:** Capable of capturing approvals made both through the traditional form (`$_POST`) and through asynchronous payloads (`application/json`) sent via AJAX by the new GLPI 10+ Timeline.
- **Modular Admin Panel:** Native interface integrated into *Setup > Plugins*, using radio buttons selectors for easy handling.
- **API Security:** Handled validations to not interrupt or break integrations via REST API or CLI (Command Line Interface) calls.

---

## ⚙️ Configuration Modes

The administrator can define three rigor levels in the plugin panel:

- **Allowed (GLPI default behavior):** The plugin remains neutral. Users can approve solutions and add comments simultaneously.
- **Show warning to the user:** If the user types a comment and clicks approve, GLPI will display a yellow warning balloon (`WARNING`) at the top of the screen, but will allow the ticket to be closed. Ideal for transition phases and user acculturation.
- **Block solution approval when there is a comment:** The strictest level. If there is typed text, the database save is **aborted immediately** and a red error notification (`ERROR`) is displayed on the screen, forcing the user to erase the text to approve, or use the refuse button.

## 🚀 Installation and Activation

**Step 1:** Download or clone this repository into your GLPI plugins folder:

```bash
cd /var/www/html/glpi/plugins/
git clone https://github.com/your-username/solutionapprovalguard.git
```

**Step 2:** Ensure write and read permissions belong to your web server user (e.g., `www-data` or `apache`):

```bash
chown -R www-data:www-data solutionapprovalguard/
```

**Step 3:** Access your GLPI panel as an Administrator.

**Step 4:** Go to **Setup > Plugins**.

**Step 5:** Locate **Solution Approval Guard** in the list, click **Install** and then **Enable** (green lock icon).

**Step 6:** Click on the plugin name to define the desired behavior and click **Save**.

## 🛠️ Cache Clearance

Since GLPI 10+ heavily stores plugin structures and views in cache (via Symfony/Twig), it is **highly recommended** to clear the system cache after installing or updating plugin files.

Run the command from the root folder of your GLPI in the terminal:

```bash
php bin/console cache:clear
```

*Or, if you need to run it with the web server user:*

```bash
sudo -u www-data php bin/console cache:clear
```

If your web server has an active opcode cache (OPcache), you may need to restart the web service to update the files in memory:

```bash
sudo systemctl restart apache2
# or if using nginx with php-fpm:
sudo systemctl restart php8.2-fpm
```

## 🧠 Technical Architecture

### Scope Hooks
The plugin uses the GLPI 10+ hook ecosystem to guarantee total coverage:
- `pre_item_update` tied to the `ITILSolution` class: Intercepts the direct click on the asynchronous approval button inside the new Timeline.
- `pre_item_add` tied to the `ITILFollowup` class: Acts as a security fallback in case the approval occurs through legacy forms or structured actions like "Add followup and close".

### Strict Table Synchronization (`getTable`)
To prevent the GLPI ORM engine from mistakenly pluralizing the table name in the database (generating incompatibilities between interface saving and hook reading), the class explicitly injects the static method:

```php
public static function getTable($classname = '') {
    return 'glpi_plugin_solutionapprovalguard_configs';
}
```

This forces the system core to strictly read and write to the exact same table, ensuring that changes saved by the administrator take effect instantly in the validation engine.

## 🔍 O Problema (Motivação)

No comportamento padrão do GLPI, quando um técnico propõe uma solução para um chamado, o requerente tem duas ações possíveis: **Aprovar** ou **Recusar**. 

Contudo, é comum encontrar um desvio de comportamento de usabilidade no ambiente de produção: alguns usuários escrevem feedbacks indicando pendências, mas clicam equivocadamente no botão **Aprovar Solução**.

**Exemplo real:**
> *"O problema foi parcialmente resolvido, mas ainda estou sem acesso a um dos sistemas secundários."* > *(O usuário escreve isso e clica em **Aprovar** em vez de Recusar).*

### Consequências:
1. O chamado é encerrado e arquivado normalmente pelo sistema.
2. A equipe de suporte assume que o incidente foi 100% mitigado (visto que o status mudou para Fechado).
3. O feedback do usuário fica esquecido no histórico do chamado, gerando retrabalho futuro e impactando negativamente os indicadores de SLA e a satisfação real do cliente.

O **Guarda de Aprovação de Solução** resolve essa contradição forçando o usuário a tomar uma decisão linear: se há o que comentar/reclamar, a solução deve ser recusada; se a solução resolveu o problema, ela deve ser aprovada com a caixa de texto limpa.

---

## ✨ Funcionalidades

- **Sanitização Inteligente de Rich Text:** O plugin limpa automaticamente tags HTML vazias (`<p></p>`, `<br>`) e entidades de espaço (`&nbsp;`) geradas nativamente pelo editor visual (TinyMCE) do GLPI, garantindo que o bloqueio só ocorra se o usuário tiver digitado texto real.
- **Interceptação Agnóstica de Requisições:** Capaz de capturar aprovações feitas tanto pelo formulário tradicional (`$_POST`) quanto por payloads assíncronos (`application/json`) enviados via AJAX pela nova linha do tempo (Timeline) do GLPI 10+.
- **Painel Administrativo Modular:** Interface nativa integrada em *Configurar > Plugins*, utilizando seletores em botões de rádio para fácil manuseio.
- **Segurança para APIs:** Validações tratadas para não interromper ou quebrar integrações via API REST ou chamadas CLI (Command Line Interface).

---

## ⚙️ Modos de Configuração

O administrador pode definir três níveis de rigor no painel do plugin:

- **Permitidos (comportamento padrão do GLPI):** O plugin permanece neutro. Os usuários podem aprovar soluções e adicionar comentários simultaneamente.
- **Exibir aviso ao usuário:** Caso o usuário digite um comentário e clique em aprovar, o GLPI exibirá um balão de aviso amarelo (`WARNING`) no topo da tela, mas permitirá o fechamento do chamado. Ideal para fases de transição e aculturamento de usuários.
- **Bloquear aprovação da solução quando houver comentário:** O nível mais estrito. Se houver texto digitado, a gravação no banco de dados é **abortada imediatamente** e uma notificação vermelha de erro (`ERROR`) é exibida na tela, obrigando o usuário a apagar o texto para aprovar, ou usar o botão de recusa.

## 🧠 Arquitetura Técnica

### Ganchos de Escopo (Hooks)
O plugin utiliza o ecossistema de hooks do GLPI 10+ para garantir cobertura total:
- `pre_item_update` amarrado à classe `ITILSolution`: Intercepta o clique direto no botão de aprovação assíncrono dentro da nova Timeline.
- `pre_item_add` amarrado à classe `ITILFollowup`: Atua como fallback de segurança caso a aprovação ocorra por meio de formulários legados ou ações estruturadas do tipo "Adicionar acompanhamento e fechar".

### Sincronização Estrita de Tabelas (`getTable`)
Para evitar que o motor ORM do GLPI pluralizasse erroneamente o nome da tabela no banco de dados (gerando incompatibilidades entre o salvamento da interface e a leitura do hook), a classe injeta explicitamente o método estático:

```php
public static function getTable($classname = '') {
    return 'glpi_plugin_solutionapprovalguard_configs';
}
```

Isso força o núcleo do sistema a ler e gravar rigorosamente na mesma tabela, garantindo que as alterações salvas pelo administrador entrem em vigor instantaneamente no motor de validação.
